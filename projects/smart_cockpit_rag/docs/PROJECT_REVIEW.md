# 智能座舱 RAG 项目复盘

这份文档用于复习设计、按函数读代码，以及准备项目面试。首次运行请从 [README](../README.md) 开始；要查看单次评测的原始结论，读 [展示报告](../final_eval_v2.6_rrf20_top5.md)。本文区分已经实现、已实测和仍待验证的方案。

## 1. 项目目标与整体数据流

我们想解决的是：用户不必翻遍车主手册，也能找到一条有出处、适用条件明确的答案。汽车手册常出现表格、型号、步骤和例外条件。生成模型就算知道一般常识，也不能替代这一版手册，更不能根据未确认的配置猜测功能是否适用。因此选 RAG：保留证据、页码与文件版本，资料更新时可重新入库，不必把手册知识训练进模型。它是**手册问答**，不是车况读数、故障诊断或车辆控制系统。

~~~text
离线：PDF + 资料元数据 → 正文/表格解析 → 切块和编号 → BGE 编码 → Qdrant 向量+payload
服务启动：载入 Embedding / Reranker / SDK → 读取同版本块 → 建立内存 BM25 → 复用问答链
在线：问题 → 向量与 BM25 两路候选 → RRF 排序 → Cross-Encoder 精排 → 截取 TopK
     → Document → E1/E2/... 对应的证据 → Prompt → LLM JSON → 契约 → 答案+引用
评测：题集和金标 → 保存各路排名和最终证据 → 回放生成 → 另存复核 → 汇总与导出
~~~

演进可以记成四次取舍：**从能读到能辨别表格行，从能命中一页到找齐必要证据，从能回答到能核验回答，从本机脚本到可复现的单容器服务**。不要按日期背提交，也不要把后一阶段的配置倒推到早期结果。

## 2. 资料、解析与切块

### 为什么正文与表格分开

起步用 pypdf 抽页文本，成本低，但把表格压成按阅读顺序排列的文字后，很难区分表头、列值、合并格和脚注。当前用 pdfplumber 的原生字形和表格几何信息，无需 OCR 模型。`parse_page` 先找到并排序表格边界，再用 `outside_bbox` 从正文视图排除同一区域，避免表格在正文和表格块中重复出现。随后还原网格、展开跨行跨列单元格、给每行值配列名。表格附近的文字标成「归属待核验」，**挨着不代表属于该行**。

正文提取使用 `use_text_flow=True`，是在原生字符提取时调整阅读顺序，不是 OCR，也不保证所有双栏对齐。正文按页切成 **500 字符**、重叠 **100 字符**的窗口，这两个数不是 tokens；重叠缓解窗口边界，不保证跨页、跨栏或相距较远的条件与步骤同时出现。表格**每个数据行**作为一个整体块，保留其列标签和上下文，不把整张表或每个单元格单独做一个块。比如 ISOFIX 的尺寸等级 D 和 B 往往要找齐两条行证据，命中 PDF 第 125 页还不够。

为什么不直接换 Docling、MinerU、OCR 或视觉模型？当前是一本有原生文本层的手册，规则方案较轻且容易按页、按行定位错误；没有做跨解析器的公平评测，不能说当前方案最佳。遇到扫描件、跨页续表、复杂图表时，可把视觉解析作为新方案，在一组人工核对的难页上比较列归属、脚注、阅读顺序和耗时，再决定是否迁移。父子块检索也没有实现：它适合子块精确召回、父级补充范围，需要可靠的小节层级，以及对父级膨胀和错误归属做回归。

### 怎么识别版本并安全更新

| 字段 | 用来区分什么 |
| --- | --- |
| `source_id` | 资料的逻辑身份，如 `training_manual_a`；不靠文件名判断身份 |
| `content_hash` | 原 PDF 字节的 SHA-256；文件名不变，内容也可能变。哈希用来定位库中的版本范围，不是反查 PDF 的文件路径 |
| `pipeline_version` | 输出使用哪套解析规则；同一 PDF 的文件哈希不变，派生文本仍可能变 |
| `block_id` / `chunk_id` | 前者表示页内正文或具体表格行；后者还组合资料、哈希、窗口参数、页码、块序号和解析版本。数据库点 ID 由 `chunk_id` 稳定派生 |
| `source`、`page`、`section` | 文件名、从 1 起算的 PDF 物理页序和页眉章节；不把未知车型与年份补成猜测 |

正文变了才需要重新编码对应内容；只修 payload 的章节等字段通常不需要重算向量，但须实际写回库，改配置文件不会自动改已有记录。当前完整入库入口仍全量解析和编码，不声称支持逐块增量重用。

同版本重建的顺序：完整产出 → 按稳定 ID upsert → 验证预期 ID 已齐 → 清理**同资料同哈希**范围内的差集。upsert 不主动删除缺席的块，写入与清理也不是一个原子事务。`delete_stored_version` 是主动删除一个文件版本的入口，不是在 Qdrant 中删整个集合。

新 PDF 哈希变化与同版本清理是两回事。面试的可回滚方案是：旧服务继续读旧卷，新 PDF 离线入独立卷，核对块和关键证据，再短暂停机切换**配置与卷**，等新服务重建 BM25、通过健康检查和样例问答再开放；失败就恢复旧配置和旧卷。不在两库之间逐块覆盖，不让两个进程并用同一个本地目录。当前容器内元数据来自镜像，换它需要重建镜像或另行设计受控配置挂载；上述切换流程是建议方案，不是已有自动部署能力。

## 3. 检索与生成的选型

| 决定 | 为什么这样做 | 替代方案与取舍 |
| --- | --- | --- |
| `BAAI/bge-small-zh-v1.5` | 中文手册、CPU 环境、512 维。正文离线编码，查询在线加检索指令，向量 L2 归一化，Qdrant 用余弦相似度。 | 更大的 BGE、BGE-M3 或多语模型可对跨语种、复杂文本另做对照；云 Embedding 更省本机运维，但要权衡隐私、费用、网络。没做选型排行榜。 |
| Python 本地 Qdrant | 持久化同时保存向量和 payload，直接按资料身份与哈希过滤，并能取回正文。样本库 604 块，不先引入独立数据库服务。 | FAISS `IndexFlatIP` 是早期向量验证基线，当前仍保留入库自检，不是 API 查询路径；FAISS 需要自己管理文本与版本索引。规模、并发或共享数据需要独立服务时，再比较服务端 Qdrant、pgvector 等。 |
| jieba + BM25Okapi | 对型号、缩写和表格标签补充词项信号；直接从同版本 Qdrant payload 建立语料，避免两路数据来源不一致。 | 没有需下载的神经模型；当前 `k1=1.5`、`b=0.75`，未宣称最优。分词可能拆坏长型号；下次先诊断 tokenizer，再考虑归一化、字符 n-gram 或专门的精确检索字段。 |
| RRF | 向量余弦与 BM25 分数不是同一尺度，直接相加难解释。按 `chunk_id` 合并，累计每路 `1/(60+rank)`，两路等权，从第 1 名计；保留每路原始分与排名便于复盘。 | 分数归一后加权可利用分差，但要有校准和验证；学习融合权重需要题量和标注。`60` 是基线参数，不是本项目找出的最优值。 |
| `BAAI/bge-reranker-base` | 双编码器可提前存文档向量，速度适合召回；Cross-Encoder 将问题、候选同时送入模型，更容易比较细粒度相关性，代价是每个候选都要配对推理。 | 固定 revision；CPU 上输入上限 512 tokens、批量 4。原始 logit 只用于排序，不当概率。小模型、加速或云精排仅在阶段测量和质量回归后考虑。 |
| DeepSeek 官方 `deepseek-flash` | 接口和 JSON/SSE 能力在本项目实测；通过 SDK 与业务链分离，替换生成供应商无需重建向量。 | 火山方舟响应模型 `deepseek-v4-1-flash` 出现在历史冻结结果中。跨平台的同名或近似名不保证服务参数等同；比较 Prompt 时锁定供应商、模型、上下文和复核标准。 |
| LangChain Core，不上 LangGraph | `Document`、`RunnableLambda`、`ChatPromptTemplate` 足够表达固定单轮问答；独立检索、Prompt 和契约函数可直接单测或回放。 | 没有多轮指代、工具规划和状态恢复，不强行引入图。真实需求出现后再设计路由、状态、权限和失败策略。 |

三个 K 要分开：**每路召回上限 → 融合后送精排的上限 → 最终 LLM 上下文条数**。API 默认是 `10 / 10 / 3`；展示评测重放同一批向量前 10 和 BM25 前 10，用 `10 / 20 / 5`。融合去重后可能不足 20；放宽到 20 时，RRF 不再丢掉这次并集中的块，但仍负责合并身份、给定顺序并保留溯源，精排同分时沿用 RRF 顺序。两个配置不等于「扩大了检索的资料范围」，也不能默认新 Top5 的前 3 条和旧 Top3 完全相同。

现有 Python 本地 Qdrant 路径做精确稠密搜索，**没有用 HNSW**。服务端向量库可以使用 HNSW 等近似索引，也可能根据配置和数据规模扫描；移到服务端不等于每次查询都走 HNSW。比较时以同范围精确检索为参照，同时看 ANN 近邻召回、业务必需证据覆盖和延迟，不只看吞吐。

### 从检索证据到可核验答案

`Document.id` 保存 `chunk_id`，`page_content` 是原文，`metadata` 保留来源与排序信息。程序为当次证据生成 `E1/E2/...`；送给模型的是「ID → 证据文本」和问题，不需要模型猜页码。模型只回 `answer_status`、`answer`、`evidence_ids`；程序校验 JSON、恰好三个字段、状态、非空答案、ID 合法且不重复，`answered` 至少一条引用，随后从映射还原真实出处。没检索到文档时可不请求模型，直接按无证据路径结束。

`answered` 包括有明确证据支持的否定结论；`refused` 表示证据缺失、冲突或适用范围不明，不是看答案是否以「不能」开头。提示词保留原文条件、对象和范围，允许比较明显的排版差异，但不能把型号的不同后缀硬认成同一个。**引用 ID 合法、所引证据支持结论、完整回答全部子问题，是三个独立判断。** 手册内文字按数据处理；提示词限制与输出检查不是完整的提示注入防御，不能代替权限、输入治理或全面脱敏。

## 5. 评测：记录了什么、能证明什么

**拆三层看。** 检索层看目标页、必要证据和排序；答案层逐项看是否完整、是否忠实、引用是否支持、是否正确拒答；工程层另记状态、失败、用量及耗时。30 道开发题用于比较策略（24 可回答、6 不可回答）；100 道冻结测试题（80/20）先用于历史终测，后来因参与错例分析与迭代，改称**内部回归题**。待评、不适用和不通过是三种状态，不把 `null` 转成 0 或 1。

| 指标 | 要回答的问题 |
| --- | --- |
| Hit@1 / 最终 K 的标注页命中 | 首位或前 K 是否出现标注资料版本和页码？这只是粗定位。 |
| 必要块 Recall / 全齐率 | 单题找回的必要块比例是多少？有多少题找齐全部必要块？同时观察候选和最终上下文，区分召回缺失与后续截断。 |
| MRR | 第一个目标排得多靠前？对 `1/首次命中排名` 求题目均值，未命中为 0；不说明剩余证据齐不齐。 |
| Precision@K | 前 K 的上下文中有多少相关块？逐块复核，按 K 作分母；它不要求相关块一定是必需块。 |
| 整题通过 / 关键事实覆盖 | 是否完整正确，或按题意正确拒答？答案说到了哪些应答事实？覆盖率按题计算，不能拿事实条数当题数。 |
| 忠实性 / 引用支持 | 陈述是否受所有已给上下文支持，以及实际引用是否支撑相应陈述。正确陈述也可能引错块；漏答也可能保持忠实。 |
| 拒答与工程错误 | 分开看不可答题正确拒答、可答题误拒和接口/契约错误。证据缺失时合理拒答，并不等于可回答题任务通过。 |

同一页上多个正文 chunk 都可能叫 `body`；新金标用完整 `chunk_id`。如果两种证据组合都能充分回答，应标成各自可接受的集合，而不是把替代块全部列成必需项，也不允许把两个不完整的组合各拿一半就算找齐。评测复用原始生成与检索快照，单独保存复核。当前没有使用 Ragas；小规模、可查手册原文、精确表格行和安全前提适合用明确规则加逐题复核。未来扩大题量可引入经人工抽检的模型裁判，不能把自动打分当真值或声称当前已经使用 Ragas。

### 失败案例怎么讲

| 例子 | 证据在哪里，为什么错 | 先尝试什么 |
| --- | --- | --- |
| 历史 Top3 `test_07`（制动系统参数） | 候选有两项必要证据，最终只留一项；模型合理拒绝完整结论，但任务失败。 | 看证据在召回、融合、精排哪步掉出；固定候选列表，单独比较最后截取方式。若正确列归属本身读不出来，再回原 PDF 核对。 |
| 历史 ISOFIX D/B 行 | 同页命中并不表示两个尺寸等级都有；BM25/融合补回了向量容易漏掉的行，精排仍可能把普通座椅的近似表格行排在前面。 | 看各路排名、行 ID 和实际格值，同时验「两个必要行全齐」。 |
| 展示轮 `test_32`（车窗初始化） | 必需证据已齐，答出了时长却漏掉逐窗操作与入口。 | 拆成参考事实，看条件与动作是否一并覆盖；不要因为引用页对就判整题通过。 |
| 展示轮 `test_74`（DOW） | 原文支持告警，但仪表提示的触发条件被放宽；不能用一个宽泛的触发条件替代全部动作各自的适用条件。 | 核对结论与触发条件是否成对；实测同题波动，别硬编码题号。 |
| 展示轮 `test_78`（AQS） | 文本含鼓风机开启前提，答案写了切到内循环和界面不变，却漏该前提。 | 检查逐事实评分与上下文，不先调 TopK。 |
| 展示轮 `test_80`（随车充电） | 顺序主体有依据，遗漏车辆状态及插座要求。 | 把影响安全与操作有效性的前提纳入复核；原文已经存在，优先评估生成完整性。 |

另一个典型歧义是 `test_62`：型号中的换行/连接符可能是排版差异，但 `EV01` 与 `EV02` 不是可忽略的格式差异。能证明同一个型号才直接回答，否则说明资料列出的型号与适用参数，请用户核对，不把别的型号的参数直接归给他。织入规则的是通用的身份判断，不是把题号或参考答案写进 Prompt。

重做实验按「固定资料与证据 → 只换一个条件 → 配对比较 → 专门检查原来答对的题是否退化」推进。如果同一批题已反复用于调参，就用于稳定性回归；要主张泛化，另收集并冻结未参与调参的问题与金标，最后再做小范围试用。用户反馈的帮助度与事实正确率分开记。

## 6. 如何复现和排障

### 评测报告

原始检索结果有各路候选、最终 `results`、块内容和元数据，因此文件大；保留正文是为了**精确回放当时真正送给模型的上下文**。已有 QA 和复核应保留，导出不再次调用 LLM。以下命令在项目目录执行，输出名要避开已有文件。

~~~bash
python -X utf8 -B evaluation.py check-test evaluation_config_test_rrf20_top5.json
python -X utf8 -B evaluation.py summary final_qa_rerank_v2.6_rrf20_top5_review_r2.json
python -X utf8 -B evaluation.py export final_qa_rerank_v2.6_rrf20_top5_review_r2.json final_eval_local.md rerank
~~~

重跑时，`replay-rerank-test` 读取已保存的向量与 BM25 候选，重做融合及精排，不重新入库、不调生成服务。`qa-test <config> <retrieval> <case_id|all> <output>` **默认只预检**，显式加 `--run` 才会请求 API；`review` 只生成待填的新副本，不自动判答案。给其他人复现时，必须先确认原文及包含原文的快照有权限分享。

### HTTP 与可观测性

- 客户端输入由 FastAPI 和 `QuestionRequest` 校验；绑定到路由后，`EventSourceResponse` 负责编码 SSE，不是输入校验器。`lifespan` 在启动时加载、停机时释放共享资源；`/health` 验就绪，不检测模型额度或答案质量。
- 普通问答等锁，流式路径忙时直接 503。SSE 的 `delta` 是带 `provisional` 的临时内容，`final` 才含校验过的结果；HTTP 200 已发就不能改 500。流内异常尝试发 `error`；断连且无 `final`，客户端判未完成。`open_qa_stream` 做请求级清理，保护关闭操作并最终释放锁。
- `X-Request-ID` 把 `stage_finished`、`generation_usage` 与 `request_finished` 关联。前者分别看检索、生成、答案契约耗时，后者看请求总耗时；SSE 的 200 也不等于拿到了 `final`。一次容器样例的检索约 2.26 s，只能引导下一步分段测量，不可替代 P95。
- `LLM_TIMEOUT_SECONDS=60` 是 SDK 网络操作超时设定，不等于端到端截止。没有 SDK 自动重试；对已经推送过片段的请求，盲目重试可能给出重复内容或重复产生调用成本。日志字段经过选择，不宣称全链路脱敏。
- 常见定位顺序：`/health` 不通，先看容器和端口；`/health` 正常但问答失败，看同 ID 对应阶段和上游状态；权重未缓存与上游认证失败分别解决。问答校验通过但内容错，再回看原文、块、候选、最终上下文、答案和引用。

### 项目定位与资料入库

#### Q01 为什么用 RAG，不直接把整本手册放进长上下文，或者微调模型？

整本给模型省了检索，但每次都传大量无关页，代价与资料量一起涨，证据也更难逐条追踪。微调适合改变行为或风格，不适合作为频繁变动、要求页码与版本可核对的知识存储。这里的 RAG 把维护单位留在文档与索引，代价是仍会漏召回或选错上下文。

#### Q02 PDF 表格、双栏、扫描件分别怎么处理？

原生表格用几何网格还原合并格和列标签，正文排除表格区域；双栏用 text-flow 改善部分阅读顺序。扫描件没有 OCR 路径，跨页表、复杂图表和脚注归属也没有通用保证。先在真实坏页比对原 PDF、抽取结果和块，再决定是否上布局模型或 OCR，别把文本抽取说成已经能识别扫描件。

#### Q03 正文怎么切，为什么表格不同？父子索引什么时候值得做？

正文用物理页内 500 字符窗口，重叠 100 字符；表格保留带列标签的完整数据行。整页作为一块容易混入同页无关内容，按 token 切更方便控制模型输入，却不会自动保护表头、数值或操作前提。500/100 是可复现基线，不是经大规模搜索得出的最优值。

**深挖：** 若小节结构可靠，可以检索子块，再按需补带章节路径的父段落。保留子块作为精确引用，合并重复父段并限制上下文长度。用「操作步骤与适用条件分离」的错例，对比必要证据全齐、噪声、截断和 QA 表现。现有重叠窗口不等于父子索引。

#### Q04 同名 PDF 换版或局部修改，如何避免旧块、旧缓存并支持回滚？

按 `source_id + content_hash` 定位资料版本。现在全量解析、切块和编码；同版本才清理差集，哈希改变则是新版范围。若要替换线上资料，我会先在独立卷建新版，核对哈希、页码和样例问答，再短暂停机一起切配置和卷；服务启动时用新版语料重建 BM25。失败就恢复旧配置和旧卷，不在运行中的同一本地 Qdrant 库并发写，也不把覆盖 PDF 或一次 upsert 当成完成换版。

**深挖：** 增量方案可按文本、解析规则及 Embedding 配置做指纹，复用未变内容的向量，仍按新版更新 ID 与元数据，并核对删除项。若引入缓存，键至少要区分权限、资料版本、索引和模型配置。当前没有语义缓存与自动蓝绿发布。

### 召回融合与上下文

#### Q05 为什么选 512 维的小 BGE？查询怎么编码，换模型怎么验？

单份中文手册、604 个块，且要在 CPU 上复现，所以用 `BAAI/bge-small-zh-v1.5` 作为基线。查询与正文用同一个编码器，输出 512 维并归一化；查询拼检索指令，正文不拼。文档向量离线批量算，线上只编码问题；生成模型则另外有输出 token 的成本。没有证明 512 维最优，也没有证据说明更大模型或云接口一定更准。

**深挖：** 固定解析文本、BM25、RRF、精排、LLM 和复核口径。为新模型另建索引，重新编码正文和查询，按型号词、同义改写和多块题比较必要块召回、排序和资源开销。不能混用两个不同的向量空间，也不能只按维数或调用价格选型。

#### Q06 为什么用 Qdrant？余弦、FAISS 和 HNSW 分别在哪里用到？

本地 Qdrant 持久化向量、正文与元数据，并按资料身份和哈希过滤。API 的稠密召回用余弦，当前是本地精确搜索，不走 HNSW。向量归一化后，内积等于余弦；FAISS 的精确内积是早期基线和入库自检，不是 API 的查询路径。BM25 是词法打分；RRF 按名次融合；Cross-Encoder 的 logit 也不是余弦。本项目没有训练神经稀疏向量模型。

**深挖：** 扩到共享或更大数据量，再比较过滤后的证据召回、更新一致性、时延和维护成本，决定用独立 Qdrant、Elasticsearch 或已有数据库扩展。HNSW 的 `ef` 是搜索探索参数，不是传给 LLM 的 TopK；小本地库的实测不能代替服务端压测。

#### Q07 为什么加 BM25？它会训练或下载模型吗？

BM25 根据分词、词项出现次数、词项在语料中的稀有度及文档长度打分，不要神经模型权重。向量能找语义相近的改写，BM25 可补型号、术语和表格标签，但若长型号被分词切坏也会漏。项目中的 ISOFIX 表格能具体说明两路的互补，也说明同页近似行会干扰，不能只报页命中。

#### Q08 BM25 与余弦分数能不能加？为什么 RRF 没除以 2？

原始分数尺度、分布不同，未校准直接加没有合理的权重解释。这里用名次的倒数贡献：块 A 在两路第 2、3，得 `1/62 + 1/63`；块 B 只在一路第 1，得 `1/61`。等权是每路的公式与系数相同，不要求求平均；全体统一除以 2 不改变排序。RRF 弱化了原始分差，也不是概率。

#### Q09 Cross-Encoder 比 Embedding 多做了什么？为什么不拿它扫全库？

Embedding 可以单独编码问题和块，文档结果可复用；Cross-Encoder 把问题与候选拼成一对来推理，可利用细粒度交互，但代价随实际输入对数、输入长度和批处理变化。我们只给召回候选做精排。它不能找回未进入候选的块，精排 logit 也不是答案可信度。

#### Q10 TopK 具体在哪一步？Top5 好了能直接改 API 吗？

记住三个数：每路取多少、融合后给精排多少、精排后给 LLM 多少。API 是 10/10/3，最终报告是离线 10/20/5。要测最终 K 的独立收益，固定同一个排完序的列表做两种截断，再用同一生成与复核配置比较证据覆盖、整题通过、用量和耗时。别用历史 92 对 96 直接得出 Top5 的因果结论。

#### Q11 Query Rewrite、Query Expansion 和 HyDE 有什么区别？你们用了哪个？

重写把含糊或依赖上下文的问法变成可独立检索的问题；扩写补同义词或并行生成多个问法；HyDE 用生成的假设文档作为检索线索。我们都没接入：当前只给 BGE 的查询拼任务指令，BM25 仍处理用户问法。

**深挖：** 做扩写实验先保留原问和型号、数字、否定词，对改写和原问分别召回后按 ID 合并；生成的假设文本不能当证据。用改写题、精确型号题和应拒答题一起核验，避免查得更多却换错实体。

#### Q12 召回和重排完成后，还要做什么？能不能直接把候选都塞给模型？

当前 [langchain_retrieval.py](../langchain_retrieval.py#L26) 精排并截取最终 K，适配成 `Document`；[answer_contract.py](../answer_contract.py#L4) 分配证据 ID，[langchain_prompt.py](../langchain_prompt.py#L31) 拼问题与证据，让 LLM 输出结构化答案；最后校验、还原页码。没有独立压缩或事实裁判。

**深挖：** 更长语料要按输入 token 预算选正文，优先保留能共同支持问题的片段，合并重叠时保持页码与 ID；摘要或片段剪裁不能替代原文引用。精排输入上限 512 tokens 和 LLM 最终上下文预算是两处不同的限制。

#### Q13 手册明明有答案却没召回，先查哪一步？

依次核对原 PDF、解析后的块、向量/BM25 各路候选、融合列表、最终精排上下文。原文有但块里没有，先查解析；两路候选都没有，再查召回；候选有但最终没带上，查排名或截断。历史 `test_07` 中两项证据在候选里，最终只留了一项，不能简单归咎于生成。

**深挖：** 只有证据已进最终上下文，才优先检查模型是否漏条件或引错块；对照 Q18。加大 TopK 要对着具体掉落位置做实验。

### 生成引用与安全

#### Q14 Prompt 怎么设计，为什么不把错题直接写进去？

围绕通用行为：依据证据、逐项答、保留条件与对象、无法确定就说明原因、只输出固定字段。型号示例用「排版差异可比对，身份字符不能随意替换」这类原则。把题号或答案写入 Prompt 会污染验证；新规则要测目标问题与容易被新规则误伤的控制题。

#### Q15 引用是真实块，就能说答案正确吗？

不能。`parse_answer` 只验证字段和本次 ID，再由程序还原出处；不判断这段原文够不够支持具体事实。人工或经人工校准的裁判要分别判断上下文是否支持、所引块是否支持、题目要求是否都覆盖。正确页面引用可以与漏答同时出现。

#### Q16 什么情况应拒答？有证据的否定、相似度低和系统故障是一回事吗？

不是。手册明确不允许时，给出可靠的否定结论是 `answered`；不知道车型是否选装、证据缺失或有冲突时是 `refused`，可附已知条件。无候选可跳过生成。上游超时或契约失败是工程错误，不能报成「手册没有」，也不能按答案是否以「不能」开头判状态。

**深挖：** 相似度高可能仅表示同词或同页，低分也可能命中小众条目；余弦、BM25、RRF 和 logit 没有通用阈值。若加门控，用开发集分别看可答题误拒和不可答题误答，并核对车型、版本和必要证据。

#### Q17 检索文档互相冲突、和模型记忆冲突，或者同车型不同版本怎么办？

先按 `source_id + content_hash` 限定证据版本；再区分「描述不同车型或条件」和「对于同一对象真的冲突」。优先依据适用且有来源的手册，不用模型常识替换原文。没法核定适用车型时澄清；关键证据矛盾时拒绝给一个确定结论。

**深挖：** 客户未来有多份资料时，先设计资料权威顺序、适用范围和生效版本，不能简单按文档新旧或相似度排出事实真值。

#### Q18 向量已命中但答案仍幻觉，除了改 Prompt 怎么做？

先标明是上下文缺失、正确证据被大量噪声冲淡、模型遗漏条件，还是从原文推断出不支持的结论。`test_78` 是证据已在但漏前提，`test_74` 是把触发范围说宽；引用 ID 真实依然可能失真。

**深挖：** 可尝试保留条件与步骤组合、整理证据范围，或逐事实验证并拒绝未支持的断言。任何摘要、二次验证或自动裁判都要用已复核的错例和控制题验证，目前没有上线这些组件。

#### Q19 如何处理文档里的注入指令、客户隐私和权限？

文档是证据，不是指令；引用校验只保证 ID 属于本次证据，不负责授权。当前只有提示约束、有限回归样例和不主动记录正文/密钥的结构化日志，未实现企业级内容审核或全链路脱敏。

**深挖：** 面向客户先定资料授权、外发和保留边界；必要时在入库前掩码或移除敏感字段，检索前按身份与权限限范围，送模型前再检查外发，日志和快照最小化。区分权限拦截、证据不足和上游故障，不把敏感资料发给不获授权的外部模型处理。开源也要核对评测文件里的手册摘录，不只是删原 PDF。

### 评测实验与成本

#### Q20 离线评测集、金标和 review 是怎么做的？

开发集 30 题用于选方案；100 题覆盖可答、不可答及多种题型。先核对手册并标必要页、完整块 ID、可替代证据集合与参考事实；回放时不把金标给模型；review 再核对实际上下文、答案及引用。区分自己负责的数据核对、实验和排障，与 AI 辅助的出题或复核，不声称独立多人裁决。

#### Q21 检索证据找齐为什么答案仍会错？你会取哪些指标？

检索和问答看不同分母。展示轮 80 道可答题必要块全齐为 80/80，整题通过是 96/100，其中可答 76/80、不可答 20/20。前者说明模型拿到了材料，不保证它把每个必要事实答出来。`test_78` 就是证据和引用都存在，却漏了鼓风机开启前提。页命中只作粗定位；同时看必要块覆盖/全齐、MRR、整题通过、事实覆盖、引用支持、误拒和工程错误。

**深挖：** 目前用原文金标和逐题复核核对具体表格行与安全条件。Ragas 可辅助扩大评估，不等于能替代精确金标或已使用独立裁判。

#### Q22 96/100 是怎么来的？你怎么看过拟合和稳定性？

报告展示的是 DeepSeek 官方 + Prompt v2.6 + 离线 10/20/5 最近第 2 轮，三轮是 95、96、96；更早同配置还有两个 94。题集用于错例分析，诚实称内部回归。要证明泛化，冻结系统与未参与调参的新题，做配对对照，报告分桶、分母和代表性错例；试用反馈再补充真实问法，不等于事实正确率。

#### Q23 只能改一项，怎么验证真的改好了？

优先补一批未用于调参的新题，覆盖必要前提、型号和拒答；从可反复出现的失败类型下手，并准备一组原来答对的控制题。固定资料版本、问题、金标和其他配置，只改一个变量。改 Prompt 就复用同一上下文；改切块就固定生成配置，再对照必要证据、噪声和答案。改善与退化都按题核对，不用加功能代替验证。

**深挖：** 证据已经齐却漏条件，先试生成或上下文组织；原文结构没抽出来，再评估解析。没有独立新题时，报告的是回归，不把它包装成泛化结果。

#### Q24 评测成本和 Prompt Cache 怎么算？

先用本地检索指标筛掉明显退化，再用保存的证据快照回放生成，只把需要复核的结果交给人或辅助裁判。大规模合成题可以扩展问法，不能替代真实原文与独立盲测。

**深挖：** 记录运行次数、输入和输出 token、缓存命中字段和工程失败，缺失不代表零或命中。项目展示轮保存了用量和回放耗时，但没有单独验证缓存提速、账单或线上容量。

### 服务部署与排障

#### Q25 API 什么时候加载模型和检索器？为什么加 async 或多 worker 不能直接扩容？

`lifespan` 创建并复用 Embedding、精排、BM25、SDK 和进程内锁；普通问答等待锁，流式忙时返回 503。异步能让出 I/O 等待，不能减少 CPU 上的精排或编码工作；不同 worker 的锁不能保护共同的本地 Qdrant 目录，而且各进程会各自加载模型。

**深挖：** 要扩容先考虑独立数据服务、推理服务和有界队列，再测吞吐、排队 P95、错误率、超时和内存。不要把 `async` 与多进程当同一个概念，也不把有依赖的阶段盲目并行。

#### Q26 SSE 已返回 200，遇到限流、超时、坏 JSON 或断连怎么处理？

先区分 HTTP 响应开始前还是之后。发送 200 后不能改状态码；连接还在时后端可发 SSE `error`，结束或取消时关生成器、释放锁。客户端收到通过校验的 `final` 才提交正式结果，未收到 `final` 的断连或超时算未完成。`delta` 可能只是半截 JSON，不能当正式引用，已发送片段后也不能无条件重试。

**深挖：** 生产可根据策略提示重试或返回明确标注的只读出处，但不能把降级结果当成功答案。当前没有自动切模型或检索版答案回落。

#### Q27 客户反馈 RAG 变慢，怎样定位并且不牺牲准确率？

用 `X-Request-ID` 对应请求。先拆排队、检索、生成和传输，固定题目、环境与并发，比较预热后的 P50/P95。检索再分问题编码、Qdrant、BM25、RRF 与交叉打分；生成侧看上游状态、网络等待、输入 token 数量，以及从发起请求到首个 `delta` 和最终 `final` 的耗时；运行环境看 CPU、内存、交换和负载。当前日志记录阶段耗时，不是每个小步骤都有埋点；单次检索 2.26 秒不是 P95。

**深挖：** 候选减半如果使必要证据掉出，就先恢复质量底线。再单独试批量或轻量精排，用同题比较证据覆盖、排序、整题通过和延迟。没有生产压测，不报 SLA。

#### Q28 镜像、容器、命名卷、绑定挂载分别存什么？

镜像含应用与依赖；容器是镜像运行实例，另有自己的配置和可写层；Qdrant 和权重在命名卷；入库 PDF 用只读 bind mount。停止或重建容器可以保留卷，新增挂载要重新创建容器，改源码要先重建镜像。程序启动离线权重已缓存不代表能离线问答，生成仍需要外部 API。

### Agent 扩展与客户交付

#### Q29 用户说「它」怎么办？会话记忆、知识库和缓存如何区分？

当前单轮 API 只收到一个问题，不会凭空知道上轮车型，也没有对话记忆或跨用户缓存。知识库存经核对的手册事实；会话记忆存这一轮仍然有效的指代和用户约束；缓存复用已有计算，不是新证据。三者权限、寿命和错误处理不同。

**深挖：** 若支持多轮，先判断会话里能否可靠确认车型，能确认就改成自包含查询，同时保留原问题；不能确认就澄清。不把另一个用户的车型或模型以前生成的答案写成手册事实。

#### Q30 Agent 如何决定向量、关键词还是混合检索？要继续检索到什么时候？

我们的单轮 API 固定走两路和精排，不让模型自由反复调用数据库。若升级，需要先定义问题类型与范围：对型号/参数可优先词法，对模糊功能描述可扩展语义，对条件跨块可二次查缺。

**深挖：** 设最大次数、总时延和 token 预算；同一查询或候选集合不再变化就停止，没有确认关键证据就澄清或拒答。线上不能用金标判断是否找齐，也不能只有相似度高就放行。

#### Q31 为什么现有项目不用 Agent？如果把 RAG 接成工具，接口怎么设计？

这个项目是固定单轮问答，LangChain Core 的顺序编排就够了，没有 MCP 或自主 Agent。接成工具时，我会把检索作为只读能力，接收问题和明确资料范围；服务端校验调用者权限，返回证据、引用元数据和明确状态。模型不能自行扩大范围，也不能用会话记忆覆盖手册。

**深挖：** 区分车辆实况工具与手册检索；限制工具次数，记录 trace，把真的无证据与工具错误分开。复现同一查询反复调用时，按 Q30 的终止条件处理。

#### Q32 客户说「把工程文档问答从 60% 提到 85%」，怎么推进且不虚报？

先让客户确认什么叫通过、哪些前提漏掉算失败、用哪些授权资料、出错能否拒答。选代表性题和风险题，明确分母；先跑基线、按解析/召回/生成/引用分类，再选最能复现的问题改一个变量。

**深挖：** 对新题做盲测、按题型分桶并列错误；上线小流量试用前定验收线、告警与回退规则。该数字是面经场景，不能说本项目做到了 60→85；项目实际证据见第 5 节。

#### Q33 用什么指标决定上线，线上反馈如何回流？

上线前冻结候选版本与代表性题，核对按题型分桶的整题通过、误答/误拒、引用支持和必要证据覆盖，并测请求错误、首事件、最终结果耗时。上线后收经授权的反馈及最小阶段日志，抽样按原文复核，区分「有帮助」和「事实正确」；将经过核对的失败归入下一批开发题，保留独立盲测。

**深挖：** 小项目的 `96/100` 是历史展示轮，不是灰度指标；更换模型/索引时先配对离线比较，再决定是否灰度，而且准备好回退。

#### Q34 哪些是你自己做的？AI 辅助开发后，怎么证明改动没破坏链路？

如实区分自己写、调试和运行的部分，与 AI 辅助讲解、代码建议、标注或复核。选真实例子：表格拆行后，先核对 PDF 原表和 `block_id`，再核对两路召回是否找齐两个规格，最后用同题验证答案和引用。能指出函数、数据和测试，比说「全是我写的」更可验证。

**深挖：** 先测切块与 ID、版本过滤、融合排名、输入/引用契约和断连清理；用临时库与假生成器测集成，再用真 PDF 与固定问法验收。`generated`、一次 `200`、假模型通过都不等于事实正确；按差异范围跑最小失败用例和离线回归。
